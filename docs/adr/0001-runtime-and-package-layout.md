# ADR 0001: Runtime and Package Layout

**Status:** decided (stage E0).

## Problem

Need a target .NET version, package split, JSON/HTTP stack, and repository layout before any
implementation can start, since these decisions shape every subsequent piece of code and can't be
cheaply reversed once endpoints are implemented against them.

## Decision

- **Target framework: `net10.0` only**, stable SDK, single TFM. `net10.0` is the current LTS
  release (supported through November 2028); `net8.0`/`net9.0` support ends November 2026, so a new
  project with long-term maintenance has no reason to multi-target them for 1.0. Native AOT,
  trimming, and additional TFMs are not declared supported without a dedicated verification pass —
  never advertised just because a normal build happens to succeed.
- **Two NuGet packages, one shared version:**
  - `XApiSharp.Net` — models, generated + hand-written endpoint clients, transport, auth, and
    other core mechanisms. Depends only on the BCL; no ASP.NET Core, database, browser, or native
    XDK dependency.
  - `XApiSharp.Net.Extensions.DependencyInjection` — `Microsoft.Extensions.DependencyInjection`
    registration. Depends on the main package plus the minimum necessary `Microsoft.Extensions.*`
    packages.
  - (Package IDs carry a `.Net` suffix relative to the working C# namespace `XApiSharp` — see the
    naming note in `docs/product-scope.md`: the bare `XApiSharp` NuGet ID is already taken by an
    unrelated package.)
- **JSON: `System.Text.Json`** — no Newtonsoft.Json dependency in the main package.
- **HTTP: `HttpClient` with externally managed lifetime** — the SDK never owns/disposes a
  `HttpClient` it didn't create itself; DI consumers use `IHttpClientFactory`.
- **Repository layout** (already scaffolded): `src/` (the two packages), `tools/XApiSharp.CodeGen`
  (dev-time only, not shipped), `tests/{UnitTests,ContractTests,IntegrationTests,PackageTests}`,
  `samples/`, `spec/` (snapshot + registry + overrides), `docs/`, `eng/` (build/release entry
  point), `.github/workflows/`. `Generated/` is a subfolder of the main package's source, not a
  separate package — generated code is compiled straight into `XApiSharp.Net`.
- **License:** MIT for original code (`LICENSE`); the vendored OpenAPI snapshot under `spec/`
  keeps its own license (X Developer Agreement and Policy) and is never relicensed as MIT.
- **Repo/CI:** GitHub + GitHub Actions. PR CI builds/tests on Linux and Windows; package
  install/consumption is additionally smoke-checked on macOS.

## Rejected alternatives

- **Multi-targeting `net8.0`/`net9.0`/`net10.0`.** Rejected: both older TFMs lose support in the
  same month as the project's earliest realistic 1.0 date, so multi-targeting would add real
  ongoing cost (conditional compilation, wider test matrix) for a support window measured in
  weeks. Can be reconsidered post-1.0 with an explicit ADR if there's real user demand.
- **Newtonsoft.Json instead of `System.Text.Json`.** Rejected: `System.Text.Json` is
  BCL-native (no extra dependency), and the model layer's requirements (SER-01..12 — extension
  data, custom converters for opaque IDs, missing/null/default distinction) are all achievable with
  it directly.
- **Single combined package (core + DI in one).** Rejected: forces every consumer — including
  non-DI console/worker scenarios — to pull in `Microsoft.Extensions.DependencyInjection` and
  friends. Splitting keeps the main package's dependency footprint at "BCL only," per the
  dependency-minimalism rule in spec section 6.3.
- **A single multi-TFM "classic" project layout instead of a `Generated/` subfolder split.**
  Rejected: generated and hand-written code need clearly different edit/regenerate rules
  (GEN-04); keeping `Generated/` as a plain subfolder inside the same project (rather than a
  separate assembly) avoids an extra public-surface boundary while still making the autogenerated
  region obvious in the file tree.

## Consequences

- No `net8.0`/`net9.0` consumers are supported for 1.0 — this needs to be visible in
  `README.md`/`docs/getting-started.md` so it's not discovered late by a user on an older TFM.
- Every dependency added to the main package beyond the BCL requires its own justification in a
  future ADR (spec section 6.3) — this ADR sets that bar, it doesn't pre-approve exceptions.
- The `.Net`-suffixed package IDs are a direct, permanent consequence of the naming conflict found
  in E0; if the upstream conflicting `XApiSharp` package is ever transferred/deleted, this ADR is
  the record of why the project didn't just wait for that and use the bare name.
